4 Form inputs

Every input type, each with a live readout of its value, so you can see the control actually registering rather than guessing. Nothing is submitted anywhere.

On-screen keyboard. Tapping a text field raises Weston's virtual keyboard, but only on a device with no hardware keyboard of its own - if a USB keyboard is plugged in, nothing appears and you type on that instead. Forced on with tessaro-ctl config set screen.osk=always, which restarts the display; journalctl -t tessaro-weston-config says what it decided. It draws over the page rather than moving it, so it can cover a field near the bottom of the screen - scroll the field up first. Everything that is a tap, a slider or a picker works with a finger alone either way.

Event source

Scroll or drag anywhere. touch means the touchscreen is reaching Chromium as touch; mouse everywhere on a touch panel means KIOSK_TOUCH or the kernel side is wrong.

Multi-touch

Put several fingers on the pad. Each tracked pointer gets a ring and its id. Only one ring with several fingers down means the panel is falling back to hid-generic, which does not decode multi-finger reports - that is what CONFIG_HID_MULTITOUCH is in the kernel config for.

6 WebSerial pending

7 WebHID pending

Same shape as serial. Opening a device subscribes to its input reports, so pressing a button on it should produce log lines.

Other device APIs

Availability only - no grants are attempted. navigator.bluetooth is absent unless KIOSK_ENABLE_FEATURES names WebBluetooth: the feature is stable on every platform except the one this is.

8 Audio playback pending

The same two-second tone in each container - 440 Hz in the left channel, 880 Hz in the right, so a single file also proves channel mapping. Audio on this image goes straight to ALSA: Chromium is built against PulseAudio but no libpulse ships, so it fails to load and falls back. There is no mixer daemon in between.

Declared codec support

canPlayType() only states an intention. A row saying probably next to a player that stays silent is the interesting failure.

9 Video playback pending

H.264 in MP4, which is what proprietary-codecs buys. A black frame with no error usually means the GPU path, not the codec: Chromium's unprivileged GPU process cannot allocate KMS dumb buffers when Weston holds DRM master, so the page loads and paints nothing.

Watch the dropped count on the 4K clip. That is the number that decides whether a panel and a board can be paired.
